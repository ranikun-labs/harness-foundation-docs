# Shared Event Envelope Contract

- Status: Draft
- Scope: Cross-service integration events
- Canonical owner: `harness-foundation-docs`
- Implementation completed: No
- Runtime supported: No
- Product released: No
- Term scope: This document belongs to the Backend Service Foundation (`DEC-057`), covering MSA backend services (e.g. Carelog, Finance Harness backend, Shared Identity). It is separate from the `oh-my-ai` AI harness product family's "Shared Platform" (`DEC-005`).

## 1. Purpose

This document defines the common metadata envelope for integration events exchanged between Harness microservices.

Foundation owns the envelope.

The publishing service repository owns the concrete event payload and business semantics.

## 2. Delivery assumption

Consumers must assume:

```text
at-least-once delivery
possible duplicate
possible delay
possible redelivery
possible out-of-order arrival
```

The envelope does not provide exactly-once processing.

Consumers must implement idempotent effects.

## 3. Canonical shape

```json
{
  "event_id": "018f6e8c-0f4d-7c21-b0d3-4f4d71f8f001",
  "event_type": "identity.account.deactivated",
  "schema_version": 1,
  "aggregate_type": "PlatformAccount",
  "aggregate_id": "018f6e8b-b7a0-73c3-b31f-9897df1b6f83",
  "aggregate_version": 4,
  "occurred_at": "2026-07-25T06:00:00.000Z",
  "producer": "identity-service",
  "correlation_id": "018f6e8a-c901-7e8f-87f4-79c65f7e7d0d",
  "causation_id": "018f6e89-90f2-7b21-a070-5a0ec8cd0081",
  "trace_id": "optional-trace-id",
  "payload": {
    "status": "DEACTIVATED"
  }
}
```

## 4. Required fields

| Field | Type | Rule |
|---|---|---|
| `event_id` | String | Globally unique immutable event identifier |
| `event_type` | String | Stable namespaced event name |
| `schema_version` | Integer | Payload schema version, starts at 1 |
| `aggregate_type` | String | Logical source aggregate type |
| `aggregate_id` | String | Stable source aggregate identifier |
| `occurred_at` | RFC 3339 UTC string | Time the business fact occurred |
| `producer` | String | Stable publishing service name |
| `payload` | Object | Event-specific data |

## 5. Conditional fields

| Field | Rule |
|---|---|
| `aggregate_version` | Required when ordering or stale-update protection matters |
| `correlation_id` | Required when the event is part of a request or workflow |
| `causation_id` | Required when another command or event directly caused this event |
| `trace_id` | Included when distributed tracing context is available |

Absence of correlation data for a truly independent scheduled event is permitted, but the producer should create a new correlation identifier for the resulting workflow.

## 6. Event identifier

`event_id` identifies one immutable event occurrence.

Requirements:

- never reused;
- unchanged across redelivery;
- generated before outbox persistence;
- used for consumer deduplication;
- not regenerated by the broker publisher.

UUID v7 is recommended when supported, but the exact identifier implementation may be standardized separately.

## 7. Event type naming

Use lower-case namespaced names:

```text
<domain>.<aggregate-or-capability>.<past-tense-fact>
```

Examples:

```text
identity.account.created
identity.account.deactivated
identity.external-identity.linked
finance.journal.created
finance.analysis.completed
carelog.customer.follow-up-scheduled
```

The name describes a fact that occurred.

Avoid transport or consumer names:

```text
send-to-finance
kafka-user-message
disable-carelog-user
```

## 8. Schema version

`schema_version` versions the event payload for a stable `event_type`.

Rules:

- starts at `1`;
- increments for incompatible payload changes;
- additive optional fields should remain backward compatible where possible;
- field meaning must not silently change;
- field removal requires compatibility planning;
- consumers must declare supported versions.

When semantics change substantially, a new event type may be clearer than a high-risk in-place mutation.

## 9. Aggregate version and ordering

`aggregate_version` represents the source aggregate version after the fact occurred.

A consumer may use it to reject stale events.

Example:

```text
local last version = 4
incoming version = 3
→ do not overwrite current state
```

Global ordering is not guaranteed.

When broker partitioning is used, `aggregate_id` is the preferred partition key for per-aggregate order.

## 10. Time semantics

`occurred_at` is the time the business fact occurred, not:

- broker publish time;
- consumer receive time;
- retry time;
- current processing time.

The publisher should preserve the original value across retries and redelivery.

Additional transport timestamps may exist outside the canonical business envelope.

## 11. Correlation and causation

`correlation_id` groups work belonging to one logical request or workflow.

`causation_id` identifies the direct command or event that caused the current event.

Rules:

- preserve correlation across service boundaries;
- set causation to the triggering message or command identifier;
- do not replace correlation on every hop;
- generate a new correlation ID when no prior workflow exists.

## 12. Payload ownership

The publishing service owns:

- payload fields;
- field semantics;
- classification of required and optional fields;
- compatibility policy;
- sensitive-data policy;
- concrete examples and fixtures.

Example location:

```text
identity-service/docs/contracts/published-events.md
```

Foundation does not define every domain event payload.

## 13. Sensitive data

The event must contain the minimum data required by consumers.

Avoid:

- passwords;
- tokens;
- credential secrets;
- full OAuth payloads;
- unnecessary personal data;
- raw journal content when an identifier is sufficient;
- unbounded free-form metadata.

Sensitive fields require:

- explicit purpose;
- access control;
- retention policy;
- encryption assessment;
- logging redaction;
- consumer inventory.

## 14. Producer requirements

A producer must:

- create the immutable envelope before outbox commit;
- persist event and domain state atomically through an outbox when applicable;
- publish without modifying event identity or occurrence time;
- document partition key;
- document schema compatibility;
- monitor unpublished and repeatedly failing outbox rows;
- retain enough evidence for replay or diagnosis.

## 15. Consumer requirements

A consumer must:

- validate required envelope fields;
- reject or quarantine unsupported schema versions;
- deduplicate by `event_id` where side effects are not naturally idempotent;
- process domain change and deduplication atomically where possible;
- acknowledge after durable completion;
- preserve correlation metadata;
- tolerate compatible additive fields;
- define retry and dead-letter behavior;
- avoid treating receive order as global order.

## 16. Event evolution

Before changing an event:

1. identify all known consumers;
2. classify the change as compatible or incompatible;
3. update the publishing service contract;
4. add compatibility fixtures;
5. deploy tolerant consumers first when required;
6. deploy the producer;
7. observe;
8. remove deprecated fields only after consumer migration.

## 17. Storage and retention

The event broker is not automatically the canonical long-term audit store.

Each system must distinguish:

- broker retention;
- outbox retention;
- consumer inbox retention;
- business audit retention;
- replay retention.

Concrete durations and partitioning belong in the owning service repository.

## 18. Initial Shared Identity events

Candidate event types include:

```text
identity.account.created
identity.account.activated
identity.account.deactivated
identity.account.deleted
identity.external-identity.linked
identity.external-identity.unlinked
```

These names and payloads remain Draft until the Shared Identity service contract is accepted.

## 19. Fixture obligations

Each concrete event should have fixtures for:

- valid current version;
- duplicate delivery;
- unknown optional field;
- unsupported future version;
- missing required envelope field;
- out-of-order aggregate version where applicable;
- redelivery with unchanged `event_id` and `occurred_at`.
